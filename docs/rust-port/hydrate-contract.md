**S-D3 residual API differences (verified against Go 1.27.4, go-sqlite3 v1.14.52, dbx v1.12.0):**
- Malformed `playlist.rules` JSON is rejected on both sides, and well-formed type mismatches are mapped to Go-shaped errors. For invalid JSON syntax, however, `serde_json` diagnostics are not byte-identical to Go `encoding/json` scanner diagnostics (for example, malformed number tokens). This text reaches the unwrapped playlist read/PUT error response. Exact scanner-message parity would require porting Go's JSON syntax scanner; it is intentionally not emulated in this scoped hydration change.
- `RowGet::get_text`/`get_opt_text` reproduce Go's `reflect.String` arm (`database/sql/convert.go:533-544`), which converts EVERY non-NULL storage class through `asString` (`:557-578`): INTEGER `7` → `"7"`, REAL → its `%g` spelling (so `2.0` → `"2"`, an infinite REAL → `"+Inf"`), and BLOB → a Go `string` of raw bytes. rusqlite's `FromSql for String` is TEXT-only (`rusqlite-0.32.1/src/types/from_sql.rs:172-177`), so the arms are spelled out in `hydrate.rs`. Verified against the pinned driver, including `cast(x'6869' as blob)` → `"hi"` and invalid-UTF-8 BLOB → raw bytes with no error. The one deliberate difference is the IN-MEMORY value: Rust stores those bytes as a `String` with per-byte `U+FFFD` replacement rather than keeping them raw, which is byte-identical to what Go's `encoding/json` emits for such a string (verified: `json.Marshal(string([]byte{0x00,0xc3,0xf8,0xff}))` → `"\u0000\ufffd\ufffd\ufffd"`); a valid NUL byte therefore differs in memory only (`"1.5\x00"` versus `"1.5\u{00}"`, same wire bytes). Scan-error messages are NOT affected: `go_quote_bytes` quotes the cell's raw bytes, so a TEXT and a BLOB cell with invalid UTF-8 both report Go's `"\xff"` spelling.
- A column declared `datetime`/`timestamp`/`date` that Go scans into a **string** field is normalized, not returned verbatim: the driver converts the cell to a `time.Time` and `database/sql` renders it through the `case time.Time:` arm's `*string` sub-arm, `*d = s.Format(time.RFC3339Nano)` (`convert.go:323-329`); `asString` is not reached for that destination. Verified against the pinned driver, reading the same column four ways: stored `2024-01-02 03:04:05+00:00` → Go `string` `"2024-01-02T03:04:05Z"`; stored epoch integer `1707246000` → `"2024-02-06T19:00:00Z"`; unparseable `not a date` → `"0001-01-01T00:00:00Z"`; and a NULL pointer column → `NULL`/`None`. `UserRecord.last_login_at`/`last_access_at`/`created_at`/`updated_at` (`user_repo.rs:539-546`) read those `datetime` columns with `get_text`/`get_opt_text` and therefore carry the STORAGE spelling instead. It is inert today — nothing marshals these fields: nd-auth's login handler serializes `LoginPayload`, whose six fields are `id`/`name`/`username`/`is_admin`/`avatar`/`token` (`login.rs:67-75`, emitted at `:155-162`), and `token_epoch` is only revalidated internally. A user-facing DTO must instead read such a column through `RowGet::get_gotime` and render it with `GoTime::to_rfc3339_nano`, which reproduces Go's `FormatTime(RFC3339Nano)` including the parsed zone; `to_go_time_text` is the UTC-normalized variant for `DateTime<Utc>` fields. Changing that now would alter `UserRow`'s field types, so it is left to the lane that adds a user DTO.
- Playlist timestamp DTO fields are strings, so Go `json.Marshal(time.Time)` errors for out-of-range RFC3339 years or zone offsets cannot currently be propagated as a whole-object serialization error. Rust still emits its normalized timestamp representation. Matching that API failure behavior requires a timestamp-aware serializer/error path beyond this row-hydration boundary; tested examples and source details are recorded in `hydrate.rs`.
- JSON numeric overflow is rejected on both sides but the playlist API diagnostics differ. Go's `encoding/json` rejects `1e400` while decoding an expression slot, and `unmarshalExpression` (`model/criteria/json.go`) surfaces `invalid expression key 'is'`; Rust propagates serde_json's `number out of range` with line/column. Both reject the criterion; the remaining difference is the error reported to the caller.
- serde_json's default 128-level recursion bound rejects deeply nested `playlist.rules` JSON that Go `encoding/json` accepts (verified with Go/Rust probes). Removing or raising that library bound is outside this hydration follow-up; this remains a reject-versus-accept difference for extreme input depth.
- Adjacent, pre-existing smart-playlist SQL diagnostics are not exact Go matches: Rust's `RangePair` and `InvalidMissingValue` errors omit the Go `, got: %v` / `: %v` value suffixes (`persistence/criteria_sql.go:218,305`). These compiler error paths predate S-D3; their diagnostic parity is outside this hydration change.
- **The JSON codecs prepend a column name Go does not.** `sql_json.rs::JsonColumnError` renders `{column}: {msg}` (pinned by `tests/sql_json.rs:340-344`), and the hooks append Go's prefix ahead of it, so a malformed cell reads `parsing album discs from db: discs: key must be a string at line 1 column 2` where Go says `parsing album discs from db: invalid character 'b' looking for beginning of object key string` (both executed). Go's own **inner** prefixes are `parsing participants:` (`sql_participations.go:65`) and `parsing tags:` (`sql_tags.go:26`), and both are reproduced verbatim — so a tags failure reads `parsing album from db: parsing tags: key must be a string at line 1 column 2` where Go says `parsing album from db: parsing tags: invalid character 'b' looking for beginning of object key string` (both executed); callers must NOT strip `parsing tags:` as port noise. The `{column}:` token itself is port-added only for the three `sql_json` codecs — `discs`, `folder_ids`, `image_files` — and `tags`/`participants` deliberately emit no token at all (`JsonColumnError::Bare`), because Go's wraps there never name the column.
- **JSON `null` in nested codec positions decodes to the zero value, exactly as Go.** `encoding/json` assigns the zero value to a non-pointer list, element, or struct field for a JSON `null` (`decode.go` `literalStore`/`array`/`struct`), while serde's derive rejects each as a type mismatch — so a plain `Vec<DbTag>`/`Vec<Participant>`/`String` field made the **port** fail a whole row that Go reads. Executed against the real `unmarshalTags`/`unmarshalParticipants`: `{"genre":null}` → `[]string{}` with `err=nil`, `{"genre":[null]}` and `{"genre":[{"id":null,"value":null}]}` → `[""]`, a top-level `null` → an empty **non-nil** map, and `{"albumartist":[null]}` / `{"albumartist":[{"id":null,"name":null}]}` → one zero participant. `sql_tags::decode_tags` and `sql_participations::decode_participants` therefore decode through `Option` fields (`RawDbTag`, `RawParticipant`); a wrong type that is **not** `null` is still rejected (`cannot unmarshal array into dbTags.genre.0` / `into participants entry 0`), matching Go's accept/reject decision. Executed port-side in `sql_tags.rs`, `sql_participations.rs` and `runtime_hydrate_album_mediafile.rs::nested_json_null_in_shims_decodes_like_go` / `::mediafile_nested_json_null_in_shims_decodes_like_go`. Evidence provenance: the `go_participants` oracle cannot express this — it marshals its own input before unmarshalling it (`main.go:138-159`), and Go's own writer never emits `null` inside these columns, so the Go side of these cases was executed in-tree against the real unexported codecs (the same method its README documents for `invalid role:`).
- Scan-side conversion messages are Go-shaped but not byte-identical, by construction. Go's driver returns the bare `convert.go` message and `database/sql` wraps it as `sql: Scan error on column index %d, name %q: %w` (`sql.go:3441, :3450`); rusqlite surfaces the wrapped payload's own `Display`, so there is no seam to inject that wrapper. `hydrate.rs::GoToInt64`, `GoToFloat64` and `UnsupportedScan` reproduce Go's inner message — including Go's `%q` over the driver value's OWN bytes, so an invalid-UTF-8 TEXT or BLOB cell keeps the `\xNN` spelling rather than a lossy decode — and append a ``" (column `X`)"`` suffix to carry the column identity Go's wrapper supplied; `NullRequired` covers Go's `converting NULL to %s is unsupported` (`convert.go:499, :511, :523, :535`) with its own wording plus the column name; `GoToBool` reproduces `driver.Bool`'s rejection (`driver/types.go:75, :81, :93, :99, :102`). Executed tests therefore assert Go's message as a contained substring, not as equality.
- **S-D3b (album + mediafile row hydration).** Four documented, evidence-based divergences, all inert for the write path:
  - `rg_*`: Go reaches `rg_album_gain`/`rg_album_peak`/`rg_track_gain`/`rg_track_peak` only through the `Rg*` dbx shims and then copies them in `PostScan` (`album_repository.go:37-38,66-67`, `mediafile_repository.go:35-38,50-53`). `row_to_album`/`row_to_mediafile` read the real column names straight onto the record, so those copies are identity no-ops; they are documented in the hooks rather than emulated with a fake shim.
  - Absent vs NULL columns: dbx hands an unmatched column a throwaway `sql.NullString` and discards it (`dbx@v1.12.0/rows.go:80-86`), so a projection that omits a shim/joined column leaves Go's zero value while a PRESENT NULL still errors. `hydrate.rs::join_text` is the single accessor both shim reads and joined-alias reads go through, and encodes exactly that split, which is why the anonymous (no-user) base read — where Go's `withAnnotation` emits only `<table>.average_rating` (`sql_annotations.go:63-66`) and `withBookmark` emits nothing (`sql_bookmarks.go:18-22`) — hydrates `SELECT media_file.*` with no joins at all over a row whose base columns are populated (executed — `runtime_hydrate_album_mediafile.rs::bulk_reads_keep_each_rows_own_id` and `::mediafile_light_queries_decode_absent_columns_to_zeros`; a row with a NULL `created_at` instead fails the required-column scan on both sides, as the timestamp bullet records). It does NOT make a light projection hydratable. For the two projections Navidrome actually emits — `get_all_ids_sql` (`SELECT id`) and `get_random_rowid_sql` (`SELECT rowid`) — neither side produces a hydrated record, which is exactly why both are read as bare ids/rowids (`queryAllSlice` into `[]int64`, e.g. `mediafile_repository.go:264-266`) and never handed to a hydrator. The failure point differs: the port fails on the first missing required column (executed: id-only album projection → `Invalid column name: library_id`); Go leaves unmatched struct fields at their zero value (`dbx@v1.12.0/rows.go:80-86`) and then the UNGUARDED `unmarshalParticipants` (`album_repository.go:48`, `sql_participations.go:61-66`) rejects the empty `participants` shim (executed through dbx v1.12.0 over `select id from album` with a real `dbAlbum`: `parsing album from db: parsing participants: unexpected end of JSON input`). That is precisely why `get_random_rowid_sql` is consumed through `queryAllSlice` and never through `ScanStruct`. Nor is this a general rule about partial projections: a projection that keeps `participants` plus a column living in the embedded struct (e.g. `id`) allocates the embed and satisfies the hook, so Go hydrates it (executed: `select id, participants from album` → `err=nil`), while the port still fails on its own missing required columns. Both sides fail a partial projection handed to a hydrator; only the reason differs.
  - Go's `model.Genre` carries `SongCount`/`AlbumCount` aggregate columns that `Tags.ToGenres` (`model/tag.go:138-148`) never fills and that no read of an album/mediafile row can populate. `sql_tags::Genre` declares only the two fields `ToGenres` actually sets (`id`, `name`), mirroring `model.Genre` (`model/genre.go:9-14`) with the counts dropped; DTOs stay nd-db-local (§6 item 4 forbids adding them to nd-model).
  - `play_count` in NORMALIZED mode (`sql_annotations.go:80-83`) is an expression column, so SQLite gives it REAL storage and rusqlite's `FromSql for i64` (Integer-only, `rusqlite-0.32.1/src/types/from_sql.rs:136-141`) would abort the read. `hydrate.rs::annotation_play_count` reproduces Go's int64 scan arm instead: `database/sql/convert.go:497-508` renders a driver `float64` through `asString` — `strconv.FormatFloat(f, 'g', -1, 64)` (`convert.go:570-571`) — then `strconv.ParseInt(s, 10, 64)`, reusing the crate's existing Go-`%g` renderer `criteria_sql.rs::go_fmt_float64`. Executed against the pinned go-sqlite3 with an `int64` destination over the real normalized expression: `play_count=7, song_count=3` (whose `typeof()` is `real` and whose `%g` is `"2"`) scans as `pc = 2, err = nil`; `play_count=1000000, song_count=1` fails with `converting driver.Value type float64 ("1e+06") to a int64: invalid syntax`; `4.1152263e+07` fails carrying `"4.1152263e+07"`. Every normalized cell is REAL storage, so the `%g` arm is the one that runs — including for integral values such as `round(7/3)`, which SQLite also reports as `typeof()` = `real`. A REAL cell whose `%g` spelling uses an exponent or keeps a fraction is therefore Go's ERROR, not a truncated integer — deliberately diverging from a truncate/round suggestion. Non-finite cells are spelled Go's way too (`+Inf`/`-Inf`/`NaN`, matching `strconv.FormatFloat(math.Inf(1), 'g', -1, 64)`): SQLite keeps the literal `9e999` as an infinite REAL even in the INTEGER-declared `annotation.play_count` column, and the normalized expression propagates it, while Rust's `{:e}` prints such values with no exponent — so the shared renderer returns Go's spelling rather than panicking. This is a **safety fix, not cosmetic reuse**: the committed version split on `e` unconditionally, so a non-finite value would abort the process (`expect("Rust scientific formatting includes an exponent")`) instead of surfacing Go's scan error — `{:e}` prints `inf`, `-inf` and `NaN` with no exponent, and an executed `catch_unwind` around the committed function confirms both infinities panic. That branch was unreachable at HEAD, because its only callers took numbers from serde_json and serde cannot produce a non-finite `f64` (`from_str::<f64>("9e999")` errors `number out of range`, `Number::from_f64(inf)` is `None`); it became live when the hydration REAL scan arms reused this renderer, since SQLite hands back a genuine infinite REAL. The `+Inf` cell in `runtime_hydrate_album_mediafile.rs` is the regression for that path. Executed arms live in `tests/runtime_hydrate_album_mediafile.rs` (finite, `+Inf`, `-Inf`); the `NaN` spelling is unit-tested in `criteria_sql.rs`, because SQLite cannot store a NaN at all — `0.0/0.0` yields NULL and `cast('nan' as real)` yields REAL `0` (CLI-verified), so no cell can reach that renderer branch through a query.

Unreachable today — nothing but `get_bool` reads those columns — so a reader added for one of them must go through the bool arm.
- **A cell that scans as Go's zero time is `None`, not a zero stamp.** For the six `created_at`/`updated_at` columns read through `hydrate.rs::go_zero_or_none` (album, media_file, folder, playlist), Go's non-pointer `time.Time` holds year-1 midnight with `err == nil` — verified: binding Go's zero `time.Time` stores `0001-01-01T00:00:00Z`, which the pinned driver parses back to `IsZero() == true`, no error — while the record's `Option<DateTime<Utc>>` has no zero-time value to hold, so the port returns `None`. That matches how the write path uses the field (`None` means "never stamped", and `mediafile_repo`/`folder_repo`/`playlist_repo::put_sql` stamp `created_at` when the record carries `None`), but it is NOT what Go's scanner reports: a reader that must expose Go's zero time literally uses `RowGet::get_dt` + `is_go_zero`, as the annotation fields and `folder.updated_at` do. SQL NULL is a separate arm and stays a read ERROR, which IS Go parity.
- **Bool scan follows the declared type.** An INTEGER cell in a column declared `boolean` — the fresh DDL's spelling for `library.full_scan_in_progress`, `library.default_new_users`, `artist.missing`, `album.missing`, `folder.missing` and `media_file.missing` — is handed back by the driver as a Go `bool` via `val > 0` (`go-sqlite3@v1.14.52/sqlite3.go:2797-2798`, after `strings.ToLower` of the decltype at `:2645`), so `2` scans TRUE and `-3` FALSE. ## 6. Seam shape recommendation

Keep it as plain functions over `rusqlite::Row` in a new `nd-db/src/hydrate.rs` (S-D owns that file + one `lib.rs` module line per §1c), no generics ceremony required. Concretely:

1. **Row reader**: a column-oriented accessor, e.g.
   ```rust
   pub trait RowGet { // or a struct wrapping &rusqlite::Row
       fn get_text(&self, col: &str) -> rusqlite::Result<Option<String>>;
       fn get_int(&self, col: &str) -> rusqlite::Result<i64>;      // NULL → error (Go parity, convert.go:499)
       fn get_i32 / get_f32 / get_f64 / get_bool ...
       fn get_opt_text / get_opt_i64 / get_opt_f64(&self, col) -> ...Result<Option<T>>; // pointer fields
       fn get_opt_dt(&self, col) -> ...Result<Option<DateTime<Utc>>>;  // route through time::optional_sentinel (time.rs:118) for imported_at-style sentinels
   }
   ```
   NULL-into-non-optional must **error**, matching Go; only the §3 pointer set gets `_opt`.
2. **Per-entity hydrator**, one per hook-bearing entity, each: map columns→fields per §2 (shim fields read from their column, unknown columns simply never read — Go discards them via `rows.go:84`, so absence is a no-op), then call that entity's **PostScan hook as a closure**:
   ```rust
   pub struct Hooks<T> { pub post_scan: fn(&mut T) -> Result<(), HydrateError> /* per-entity */ }
   ```
   with the hooks in `hydrate.rs` (or entity modules) as `pub fn album_post_scan(row, album: &mut AlbumRecord) -> ...` etc., doing exactly what the Go hooks do — including the two *delegating* hooks: `playlist_track_post_scan` and `scrobble_buffer_post_scan` both call the **shared mediafile hook first**, then apply the overwrite:
   ```rust
   track.media_file.id = track.media_file_id;  // playlist_track_repository.go:32
   entry.media_file.id = entry.media_file_id;  // scrobble_buffer_repository.go:28
   ```
   The overwrite is just data movement *after* the delegation, so it needs no special mechanism — a two-step hydrator (`hydrate_mediafile` then overwrite) is faithful and testable. The hooks must preserve Go's guards exactly: `!= ""` before unmarshal for `discs`/`tags`/`folder_ids`/`image_files`/`libraries_json`/`rules`/`library_stats_json`/`similar_artists`; **no** guard for `participants` (Go calls `unmarshalParticipants("")` and it succeeds).
3. **Marshaller**, per entity:
   ```rust
   pub fn album_row(e: &AlbumRecord) -> (Vec<String>, Vec<Value>)  // returns sorted cols, positional values, id NOT included
   ```
   implementing PostMapArgs inside: compute derived columns, marshal JSON columns, apply the deletions (artist's `sort_artist_name`/`mbz_artist_id`; playlist's `rules`-vs-counters), then sort the keys (Go sorts the **final** map; use a `BTreeMap` before converting to pairs so the ordering matches `sort.Strings`).
